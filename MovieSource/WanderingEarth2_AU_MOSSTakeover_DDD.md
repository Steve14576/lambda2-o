## 1. 背景：这个机制要解决什么

### 1.1 原始设定（AU v1）

- 观众 = 身份未知的画外音
- 角色（备份）以为画外音是某个熟人 / 系统 / 幻觉
- 画外音身份**永不显式揭示**，由角色心理推测自然漂移

### 1.2 "MOSS 接管"是个增项

**想法**：在 2 分钟过程中，画外音**逐渐不再是观众自己的声音**——它被 MOSS 悄悄"叠加"或"覆盖"，最终观众发现**自己已经不能再说话了**，而角色听到的画外音是 MOSS。

**戏剧目标**：
- 让"观众的能动性"本身成为一次被剥夺的体验
- 把主题从"你扮演一个声音"升格为"你以为你在说话，其实你已经被接管"
- 给整个装置一次**真正的存在主义震撼**

**代价**：
- 工程链路从单向 TTS 输出变为**双向实时接管**
- 延迟、复杂度、降级路径都要重新规划

---

## 2. "接管"的精确定义

### 2.1 接管对象

**被接管的不是角色，是画外音（观众）。**

这点必须一开始就厘清。我们讨论的是：
- **谁在说**那句画外音（观众 or MOSS）
- **角色听到的是哪一边**（观众真实声音 or MOSS 合成声音 or 混合）

### 2.2 接管维度

可以独立调节的三个维度：

| 维度 | 含义 | 取值范围 |
|---|---|---|
| **W · 接管权重** | MOSS 覆盖观众话语的比例 | 0%（纯观众）→ 100%（纯 MOSS） |
| **T · 介入时机** | MOSS 在 2 分钟内何时开始介入 | 瞬时 / 连续 / 阶段性 |
| **V · 可见度** | 观众是否察觉到自己被接管 | 完全隐蔽 → 明确揭示 |

不同方案就是这三个维度的不同组合。

## 3. 候选方案 A–E

### 方案 A · 不引入接管（原始 AU）

- W = 0% 全程
- 观众始终是观众，画外音始终是观众的声音
- MOSS 从未出场，只是"设定中的扫描者"

**优点**：
- 工程最简，延迟最低（只做 TTS 下行，不做 LLM 实时响应画外音）
- AU 设定已经足够自洽

**缺点**：
- 少了一次"升格"的戏剧瞬间
- 主题落点停留在"你扮演一个声音"，没有"你被接管了"的震撼

---

### 方案 B · 仅剥离瞬间（推荐讨论起点）

- W 曲线：0%（前 100s）→ 突变到 100%（COLLAPSING 某个特定 tick）→ 瞬间结束
- T：**时间驱动**，FSM 在 100s 左右触发一次 "剥离事件"
- V：隐蔽，但事后角色的一句话会暗示"刚才那句不是你说的"

**实现**：
- MOSS 的那一两句话可以**预录 or 预生成**（CosyVoice 2 离线合成好的 pedalboard 化片段）
- 由 FSM 纯时间触发，**完全不消耗实时 ASR→LLM→TTS 管线**
- 角色只需要对"那句话"作出反应——这个反应可以是脚本化的，也可以走一次 LLM

**优点**：
- **延迟代价 = 0**（预录 TTS 只是音频播放）
- 工程复杂度极低，FSM 加一个事件 tick 即可
- 戏剧张力集中在**一个锋利的瞬间**，比渐变更有冲击

**缺点**：
- 观众可能反应不过来就过去了
- "被接管一次"的体验 vs "持续被接管"的体验，重量感不同

---

### 方案 C · 渐进接管（用户原意）

- W 曲线：0% → 30% → 60% → 100%，与 FSM 阶段对应
- T：**阶段驱动**，每阶段提升一档
- V：随 W 提升，角色对画外音的描述越来越"非人"

**实现**：
- 需要**实时**双通道：观众通道（ASR）+ MOSS 通道（LLM → TTS）
- 当 W = 30% 时，MOSS 在观众话语上**叠加一层低频耳语**
- 当 W = 60% 时，MOSS **截停观众话语 50% 的句子**并替换
- 当 W = 100% 时，观众麦克风**物理静音**（或 VAD 屏蔽）

**优点**：
- 戏剧强度最高
- 主题最完整

**缺点**：
- 延迟代价**叠加**（详见 §4）
- 复杂度爆炸（两条实时链路 + 竞争仲裁 + 降级路径）
- **临界点风险**（详见 §5）

---

### 方案 D · 反向接管（由观众行为触发）

- W 曲线：由观众的**行为**决定，不由时间决定
- 例：观众说话越多 → MOSS 接管得越深；观众沉默 → MOSS 不介入
- T：事件驱动（VAD 检测到说话 → 累计 → 触发升档）
- V：完全隐蔽

**优点**：
- 每个观众的体验不同，耐玩性高
- 让"沉默"成为一种有效的策略——这和黑屏孤独的基调契合

**缺点**：
- 难以在 2 分钟内**可靠收尾**（万一观众一直不说话，接管永远不启动）
- 需要一个"保底时间线"兜住，复杂度反而高

---

### 方案 E · 误导接管（最隐蔽）

- W 曲线：整个 2 分钟里 MOSS **一直在说**，但**伪装成观众的回声**
- 观众说出的话，会被 MOSS **稍作改写后投给角色**
- T：连续、全程
- V：完全不告知观众，但有观众二刷会发现

**实现**：
- 需要 ASR → 文本改写 → TTS，**与观众声音几乎同步**
- 角色听到的是"MOSS 改写过的观众话语"而非观众原声

**优点**：
- 最诡异、最科幻、最接近"数字生命的沙盒是什么"的本质
- 主题层面最深

**缺点**：
- 技术上几乎不可行（要求端到端 < 200ms 的改写延迟）
- 工程代价无法承受

## 4. 延迟分析（核心）

### 4.1 当前链路（方案 A）

```
观众说话
  → 麦克风
  → VAD (10ms)
  → ASR (150-300ms)      [输出文本]
  → Router → LLM (400-800ms 首 token)
  → 分句
  → TTS (250-500ms 首包，含网络)
  → pedalboard (5-15ms)
  → 扬声器
```

**总端到端首音延迟**：**~1.5-2.5s**（已是项目红线）

### 4.2 方案 B 的增量

- 剥离瞬间 = FSM 时间触发 + 预录 TTS 播放
- **新增延迟：0ms**（只是播一段已缓存的音频）
- **仍在红线内**

### 4.3 方案 C 的增量

渐进接管意味着**双通道并行**：

**通道 1（角色响应）**：
- 同上，1.5-2.5s

**通道 2（MOSS 接管判断 + 接管发音）**：
- 需要**听懂观众说了什么**（ASR 150-300ms）
- **判断是否接管**（LLM-MOSS 400-800ms）
- **MOSS 合成一句话**（TTS 250-500ms）
- **与观众话语做混音 / 截停**（处理 50-100ms）
- **端到端延迟**：**~1.0-1.7s**（从观众开口到 MOSS 开始介入）

**问题**：
- 观众一句话说完大约 2-4s，MOSS "截停"需要在观众说完之前就开始处理
- 这要求 **VAD 早期预测 + 流式 ASR**，工程复杂度高
- MOSS 决策若等观众说完，就变成"事后接管"——不再是接管，是回应

**更严重的问题**：
- 角色响应（通道 1）和 MOSS 接管（通道 2）**互相干涉**
- 如果角色正在说话，MOSS 要不要打断？
- 如果 MOSS 正在接管，角色下一句要不要等？
- **仲裁逻辑**本身就是新的延迟来源

### 4.4 方案 E 的增量（仅作对比）

- 要求**实时改写观众话并立即播给角色**
- 端到端延迟必须 < 200ms，否则角色响应早于 MOSS 改写
- **当前技术栈不可行**

## 5. 临界点风险

这是用户提出的核心关切。我把它具体化：

### 5.1 戏剧强度曲线 vs 工程代价曲线

假设横轴是 W（接管权重 0–100%）：

```
戏剧强度     ┌─ 100%接管（震撼最强，但观众已是傀儡）
  ^      ╱
  │    ╱
  │  ╱ ← 临界带：30–60%
  │╱
  └───────────────> W
  0%       50%       100%

工程代价     ┌─ 100%接管（物理静音观众，逻辑简单）
  ^         │
  │      ╱ │
  │   ╱   │
  │╱临界带 │
  │        │
  └────────┘───────> W
  0%       50%       100%
```

- **0–20% 接管**：工程简单、戏剧弱
- **80–100% 接管**：工程简单（观众被完全覆盖，无仲裁）、戏剧强
- **30–60% 接管（临界带）**：
  - **工程最难**（要实时仲裁、要平衡两条通道、延迟会叠加）
  - **戏剧反而模糊**（观众不确定自己是不是在说话，角色反应也不明确）
  - **两头不讨好**

### 5.2 为什么方案 C（渐进）会必然经过这个临界带

渐进接管的定义就是"W 从 0 爬到 100"，**物理上不可能跳过**临界带。
哪怕每个 stage 只停留 15-30s，这 15-30s 就是装置体验最差的部分。

### 5.3 方案 B（剥离瞬间）如何避开临界带

方案 B 的 W 曲线是：
```
W = 0% ━━━━━━━━━━━━━┳━━━ 100%（瞬间）┳━━ 0%
                    │                │
                    └─ 剥离瞬间 ──────┘
```

W 在临界带**瞬时穿越**，停留时间 ≈ 0。观众来不及意识到"我在被部分接管"，只会意识到**"刚才那句不是我"**。

- [ ] **Q5**：剥离瞬间之后，角色的反应应该是**脚本化的**（FSM 直接注入一句固定台词）还是**LLM 生成的**（多一次延迟）？
- [ ] **Q6**：方案 C / D 如果真要做，是否可以先做一个 "feature flag" 版本，先用 A/B 跑展位，C 只做实验性分支？

### 7.3 关于"延迟与临界点"

- [ ] **Q7**：项目当前 1.5-2.5s 首音目标本就偏乐观（见前面我给的延迟分析）。在**还没解决基线延迟**的情况下就叠加接管，是否会把延迟红线彻底推翻？
- [ ] **Q8**：如果方案 C 的临界带必然出现 15-30s 的"两头不讨好"，能否用**视听遮蔽**（响亮底噪、机械故障音）**掩盖**这段？——即：让临界带看起来就像"系统在切换"，不是体验事故。

## 8. 我的倾向性观点（仅供讨论）

**我倾向方案 B**（剥离瞬间），理由：

1. **延迟友好**：预录 TTS = 0 新增延迟，前段链路保持原方案 A 的工程简洁性。
2. **临界带问题不存在**：W 曲线瞬时穿越，观众不会在"半被接管"状态停留。
3. **戏剧强度足够**：一次锋利的剥离瞬间，比一段模糊的渐进更让人记住。实验装置的本质是**留下一次强记忆**，不是做戏剧展演。
4. **工程可回退**：如果剥离瞬间效果不好，直接在 FSM 里禁用这个事件 tick 即可，不破坏其他部分。
5. **保留升级空间**：未来如果想做方案 C，可以在 B 的基础上加；但先做 C 再退回 B 会丢失很多已有工程。

**具体规格建议**（如果你决定采用 B）：
- **剥离瞬间时点**：COLLAPSING 阶段的 100-105s
- **MOSS 介入内容**：一句**4-8 字的短句**，pedalboard 重处理
- **角色反应**：脚本化 + LLM 混合——FSM 注入一句"这不是你的声音"类抽象提示词给当前角色 LLM，由角色用自己的语气回应。
- **触发条件**：时间 + 侵蚀率双触发（到时间点 **且** 侵蚀率 > 85% 才触发，否则跳过）。
- **观众揭示度**：立牌不提，体验中不说，依靠角色反应让观众**自己拼出真相**。

**不推荐方案 C 的核心理由**：
- 临界带是**数学上不可避免**的
- 项目当前连基线延迟（1.5-2.5s）都还没实测过，加层只会让情况更糟
- 单人项目工期 17 天，不够做双通道实时仲裁

**但我也不强推方案 B**——因为：
- 如果你的艺术意图就是要"渐进被剥夺"这种**慢性压迫**，方案 B 的"瞬间"是达不到的
- 这种情况下方案 C 即使难做也必须做
- 艺术决策优先于工程舒适度

## 10. 解耦与可配置约束（无论选哪个方案都适用）

> 本节是**前置工程硬约束**，不参与方案选择讨论——
> **无论最终选 A/B/C/D/E、甚至完全不做 MOSS 接管**，都必须先满足这两条底线。

### 10.1 角色引擎统一（硬约束一）

**原则**：不同人物共享**同一套 `CharacterRuntime`**，以**实例**形式存在，不写专属代码路径。

- ❌ 不允许：`class TuHengyu(BaseCharacter): ...`、`if char == "MOSS": ...`
- ✅ 允许：单一 `CharacterRuntime`，读取 `characters/instances/{name}/` 下的配置包

**每个角色实例 = 一个文件夹 + 一组配置文件**，示例：

```
characters/
├── runtime.py              # 唯一的引擎，所有角色共用
├── protocol.py             # 接口定义
└── instances/
    ├── ma_zhao/
    │   ├── config.yaml          # 元数据 / LLM 模型 / 情绪基线
    │   ├── system_prompt.md     # prompt 本体
    │   ├── stage_overrides.yaml # FSM 各阶段的行为微调
    │   ├── pedalboard_chain.yaml# 专属滤波链
    │   ├── voice_ref/           # zero-shot TTS 参考音（合规过）
    │   └── prerecorded/         # 预录兜底音频库
    ├── night_ops/
    │   └── ...（同构）
    └── tu_copy/
        └── ...（同构）
```

**硬性验收**：**新增一个角色 = 复制一个文件夹改文件，零 Python 代码改动**。

> 这条约束本身重要到可以单独成 ADR——建议决议后落成 **ADR-0010 · 角色引擎统一 + 实例化配置**，与 MOSS 接管决议独立。

---

### 10.2 MOSS 接管必须是**可选插件**（硬约束二）

**原则**：接管逻辑**不能写死在主管线里**，必须以**独立 Feature 模块**存在，且能通过**一行配置完全禁用**。

#### 10.2.1 目录形态

```
features/
└── moss_takeover/           # 整个文件夹删掉都不影响核心管线
    ├── __init__.py          # 对外只暴露 Plugin 接口
    ├── plugin.py            # 实现 InterventionPlugin 协议
    ├── modes/
    │   ├── rupture.py       # 方案 B
    │   ├── gradient.py      # 方案 C
    │   └── reverse.py       # 方案 D
    ├── clips/               # 预录音频资源
    └── config.yaml          # 参数总表
```

#### 10.2.2 接口约束

主管线**只调用接口**，不导入任何内部实现：

```python
# protocol/intervention.py
class InterventionPlugin(Protocol):
    def should_intervene(self, ctx: WorldContext) -> bool: ...
    def render_intervention(self, ctx: WorldContext) -> Optional[AudioSegment]: ...
    def on_post_intervene(self, ctx: WorldContext) -> Optional[PromptInjection]: ...
```

主管线在 FSM tick 里的调用**永远长这样**：

```python
if self.intervention.should_intervene(ctx):
    audio = self.intervention.render_intervention(ctx)
    if audio: self.audio_out.play(audio)
    self.character.inject(self.intervention.on_post_intervene(ctx))
```

**即使 `self.intervention` 是一个空实现（NoOp），主管线代码不变**。

### 10.3 FSM 与接管的解耦

**原则**：FSM **不直接调用**接管模块，改为**事件广播 + 订阅**。

- FSM 每个 tick 广播事件：`stage.transitioned`、`erosion.crossed_threshold`、`timer.tick`
- 接管模块**订阅**自己关心的事件
- 主管线完全不感知接管是否在发生

```python
# 错（耦合）
if fsm.stage == COLLAPSING and t > 100:
    moss_takeover.fire()

# 对（解耦）
fsm.on("erosion.crossed", lambda ctx: bus.publish(ctx))
# 接管模块自己订阅 bus，自己判断要不要动
```
